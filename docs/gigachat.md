# Эмбеддинги GigaChat

GigaChat используется только для эмбеддингов FAQ и LightRAG. Текстовые ответы,
построение графа моделью и разбор PDF остаются на выбранных ранее провайдерах.

В «Подключения → Модели → GigaChat» superadmin задаёт:

- ключ авторизации (Basic credentials из кабинета GigaChat, не access token);
- тип доступа: GIGACHAT_API_PERS, GIGACHAT_API_B2B или GIGACHAT_API_CORP;
- одну модель эмбеддингов для FAQ и графа. По умолчанию EmbeddingsGigaR:
  контекст4096 токенов, вектор2560. Embeddings/Embeddings-2 — вектор1024.

Ключ шифруется в PostgreSQL с SETTINGS_ENCRYPTION_KEY и не возвращается API.
Проверка подключения отправляет небольшой запрос эмбеддинга. Клиент получает
OAuth-токен на официальном endpoint, кеширует его до истечения и обновляет
однократно при401; параллельные запросы одного процесса делят токен и lock.
Ошибки не содержат upstream body, ключей и access token.

TLS проверяется всегда. Публичные корневой и выпускающий сертификаты Минцифры
применяются только к HTTP-клиенту GigaChat, системное хранилище не меняется.
Файлы сертификатов и источник описаны в llm/providers/certs/README.md.

## Переход наполненного стенда

Векторы разных моделей несовместимы даже при одинаковой размерности. Простая
смена селектора в админке для наполненной базы блокируется. Для текущего
файлового JSON-хранилища есть управляемая офлайн-процедура:

1. Убедиться, что обработка документов завершена. Сохранить свежий pg_dump -Fc,
   files volume и инфраструктурные секреты. Проверить читаемость копий.
2. Выбрать **один** стенд. На хосте взять эксклюзивный
   `/run/lock/abitur-deploy.lock` через `flock` **до остановки сервисов** и держать
   до завершения миграции и согласованного запуска. Это тот же lock, который
   использует CI; без него автодеплой может запустить процессы во время пересчёта.
   Все команды остановки, пересчёта, проверки и запуска выполнять внутри одной
   сессии `flock /run/lock/abitur-deploy.lock sh -eu` (из интерактивного SSH).
   Остановить API, bot и scheduler выбранного стенда, включая другие
   процессы/хосты с доступом к этому же хранилищу. Не останавливать соседние вузы.
3. Из образа с этой версией кода, с env/томами выбранного стенда, выполнить
   `uv run --no-sync python -m tools.reembed_gigachat --offline`, подав JSON
   с GIGACHAT_API_KEY, GIGACHAT_SCOPE и GIGACHAT_EMBEDDING_MODEL через stdin.
   В Docker использовать `compose run --rm --no-deps -T api ...`, чтобы команда
   не запустила остановленные сервисы по depends_on. JSON хранить в файле0600
   вне checkout; не передавать ключ в аргументе, issue, transcript или CI.
4. Скрипт также берёт неблокирующий lock на общем data volume, отклоняя второй
   параллельный запуск миграции. Он проверяет модель, заново считает каждый вектор чанков, сущностей,
   связей и вопросов/синонимов FAQ. Тексты, ID, граф, метаданные документов и
   настройки текстовых моделей сохраняются. До подготовки всех векторов
   активный индекс не меняется. Частичная/повреждённая база вызывает отказ.
   Наборы ID сверяются с каноническими чанками, узлами и связями графа; отсутствие
   файла или отдельных строк не принимается за пустое хранилище. Производный
   кеш старых RAG-ответов в новом индексе очищается.
5. После подготовки заменяются текущий индекс и единый кеш FAQ, затем
   сохраняются оба назначения провайдера `gigachat` и ключ. Параллельных
   рабочих кешей для разных моделей нет. Старый индекс хранится только в
   резервном каталоге embedding-migration-* рядом с корнем LightRAG.
6. Возвращённый JSON должен содержать новую revision, модель, размерность,
   количество пересчитанных векторов и путь backup_directory; в нём нет ключа.
   Успех дополнительно отмечен файлом completed.json в резервном каталоге.
7. Запустить API и bot выбранного стенда. Проверить связь, обработанный документ,
   поиск по нему и FAQ. Проверить, что text model и настройки другого вуза
   сохранились. Передавать следующий стенд на миграцию только после проверки.

Для кеша FAQ в Compose задан FAQ_EMBEDDINGS_CACHE_PATH=/app/data/faq_cache.pkl,
общий для API/бота этого вуза. Файл заменяется атомарно. При смене модели кеш
пересчитывается целиком; кеш старой версии без сведений о модели тоже заменяется.
Ключи разных вузов/тома не объединяются. PostgreSQL-режим LightRAG этой
офлайн-командой не поддерживается и отклоняется до изменения данных.

## Сбой и восстановление

До замены индекса ошибка оставляет исходные данные и настройки в прежнем виде.
Сохраните диагностический каталог и проверьте причину; сообщения CLI намеренно
не выводят сырые исключения с секретами. Не публикуйте файлы резервной копии.

Публикация файлов и commit PostgreSQL не образуют общую транзакцию. При сбое
между ними **не запускать процессы экземпляра**. prepared.json описывает готовый
индекс, settings-before.json содержит прежний зашифрованный снимок настроек,
old-index и old-faq-cache.pkl — прежние данные; needs-recovery.json отмечает
неподтверждённый commit. Проверить фактическую revision/провайдеры в БД: потеря
подтверждения commit не доказывает, что он не выполнен.

Восстановить согласованную пару: прежний индекс/кеш и прежний снимок настроек
с сохранённым SETTINGS_ENCRYPTION_KEY, либо закончить переключение на полностью
подготовленный новый индекс. Восстановление выполнять при остановленных
процессах только выбранного стенда. Одна подмена image или одного селектора
не является откатом векторного пространства.
