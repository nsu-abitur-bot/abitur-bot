## Подтверждённая безопасная оптимизация

До правки `set_status` и каждый разрешённый throttle-ом `update` ожидали
Telegram `send_message_draft`. Callback вызывается с `await` внутри чтения
стрима модели. Поэтому RTT/зависание draft задерживали и начало поиска,
и дальнейшее чтение стрима. Это доказано тестом
`test_slow_drafts_do_not_block_generation_or_final_delivery`: до правки он
падает с TimeoutError, после проходит при навсегда заблокированном draft.
Это **подтверждённый механизм**, но его вклад в конкретные 30 с на prod неизвестен.

После правки один фоновый worker отправляет draft, хранится только последнее
ожидающее обновление. Финальная отправка, ошибка и отмена handler отменяют
worker; финальный текст отправляется прежним путём с прежним split/HTML fallback.
Промежуточные статусы могут объединяться. Текст ответа, промпты, поиск, модель,
правила ответа и ограничения частоты token updates не меняются.

Контролируемый локальный эксперимент: fake transport, ровно 50 мс на сетевой
вызов, 3 статуса + 2 token update + final, `min_interval=0`, 30 повторов каждого
варианта. Сравнивается старый TelegramStreamer из baseline SHA и новый класс:

| Вариант | n | Медиана, мс | p95 nearest-rank, мс |
|---|---:|---:|---:|
| До | 30 | 306,84 | 314,21 |
| После | 30 | 51,01 | 51,63 |

Это изоляция последовательных RTT (в реальности token throttle = 1,2 с),
**не прогноз ускорения prod**. Скрипт `compare_drafts.py` и JSONL лежат в `/tmp`.
Регрессионный сценарий: тестовый вопрос про документы, медленный/сломанный
Telegram draft, FAQ/RAG и модель продолжают работу, человек получает тот же
финальный ответ; промежуточный worker завершён. Дополнительно проверены
объединение обновлений, отказ draft, прежний fallback и отмена handler.
Содержательная логика ответа не менялась; существующий offline-набор проходит.

## Диагностика после разрешённой выкладки

`abitur.latency` пишет INFO `latency {JSON}` в обычный application log.
Случайный `request_id` объединяет Telegram, pipeline, фоновые задачи и
`asyncio.to_thread`; он не содержит chat/user/session ID. Поля: `stage`,
`duration_ms`, `status=ok/error/cancelled/observed`, `error_type` (только класс).
Аргументы функций, тексты, URL, ответы, exception message и ключи не пишутся.
`latency_request` содержит `process_first`; это первый вход в процессе,
**не гарантия холодного графа**. У процессов api/bot независимые флаги.

Этапы:

- `telegram_update_age`: от timestamp Telegram до handler (точность исходной
  даты — секунды, включает доставку/очередь/расхождение часов, не чистую сеть).
- `telegram_total`, `telegram_typing`, `telegram_draft`, `telegram_send`.
- `pipeline_total`, `history_write`, `history`, `faq`, `faq_embedding`.
- `retrieval_total`, `graph_acquire`, `search_embeddings`, `rag_embedding`,
  `rag_model_call`, `source_titles`, `source_ranking`, `source_ranking_model_call`.
- `crag_total`, `crag_filter`, `crag_grade`, `crag_model_call`,
  `crag_refine`, `crag_refine_model_call`.
- `generation_tools_total`, `generation_first_delta`, `tool_execution`,
  `answer_total`, `intent_background`, `intent_model_call`.

Вложенные/параллельные времена **не суммировать**. `search_embeddings` включает
поиск и возможный keyword LLM LightRAG; вложенные spans показывают их доли.
`generation_first_delta` — до первого непустого текстового delta, включая tool
раунды перед ним; для FAQ его нет. FAQ/RAG fallback может дать успешный внешний
span при ошибке вложенного вызова. Отмена draft перед final ожидаема.

Счётчики `*_model_call` — логические вызовы на границах приложения, не HTTP
попытки SDK. `generation_tools_total` охватывает весь tool-loop; внутренние
генерации и retries SDK отдельно не наблюдаются. Их время входит в wall time,
терминальный timeout виден как класс исключения. Число retries/внутренних
tool-round генераций **неизвестно**, нельзя выдавать число spans за число HTTP
запросов. Реестр/провайдеры параллельной #377 не менялись.

Для дальнейшего сравнения нужны разрешённая выкладка диагностики и тестовый
контур с копией KB: тот же набор вопросов, отдельно FAQ hit/miss и tool path,
первый полный запрос после рестарта и повторные, n/errors/median/p95 по каждому
этапу и полному Telegram пути. Нужен больший заранее ограниченный период для
оценки p95 и ошибок. Без этого нельзя объявлять причину 30 с установленной или
цель end-to-end задержки достигнутой. #219, #289 и #242 остаются отдельными.
