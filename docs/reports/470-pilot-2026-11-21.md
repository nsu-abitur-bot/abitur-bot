# Проверки #470 от 21 ноября 2026

Пилот остановлен при подготовке FAQ из-за ошибки Cloud.ru без подтверждённого
usage. Два вопроса завершены, четыре не выполнены. Подключения закрыты,
неопределённый резерв сохранён. Задача #470 остаётся открытой.

  digest `sha256:c01cf499ff7ec2564bbc8cd4486fad131c806c3297b3cc0997fef0721bf3b5f0`.

  `78531e1d41ba70bd16dc4a5823974261d598910d51fef569fd8eb384589baf58`.

  Рабочие стенды и #388 не перенастраивались.

Использован разрешённый `run pilot` со штатным root-owned bootstrap. Вопросы
подавались в `ask_local_llm` как синтетический вход worker, без изменения текста
и хешей. Ответы форматировались штатной функцией и доставлялись штатным
TelegramStreamer настоящему согласованному получателю. Его идентификатор
использовался только для маршрутизации и не попал в отчёт.

Это проверка pipeline, форматирования и Bot API delivery. Вход через Telegram
polling и BotCore не проверен. Поэтому результаты не означают успешную проверку
всего пользовательского пути.

## Остановка на подготовке FAQ

Отдельный API worker создал временную запись через настоящий маршрут
`POST /api/v1/faq`, статус201. Использовался временный администратор из
изолированной БД, вход выполнен через настоящий `/api/v1/auth/login`.
Пароль и JWT не сохранялись и не выводились, администратор удалён после операции.
UUID временной записи сохранён только в закрытом manifest на сервере.

При следующем запуске worker загрузка нового FAQ потребовала embedding.
Попытка58 относится к **setup**, не к вопросу faq-1. Ответ HTTP и usage не
получены, CloudRuError произошёл через5,3574с. В квитанции нет
question_started_at_utc: сам FAQ-вопрос до pipeline не дошёл.

Ограничитель сохранил резерв94embedding-токена /0,003029₽ и выставил halted.
Worker вернул137. При минимуме доступной памяти997,5МиБ host floor300МиБ
не срабатывал. Код137 сам по себе не доказывает OOM: watchdog также останавливает
worker при остановке учёта. Причина транспортного сбоя Cloud.ru пока не установлена.
Runtime-логи и секретные файлы для её восстановления не читались.

Следующие шаги цепочки не запускались:

- faq-1 иfaq-2 с доставкой ответа.
- Правка v1 -> v2, обновление горячего кэша и время распространения.
- Отдельные tools-1 иtools-2, включая get_admission_scores.

Вызовы get_education_programs в двух RAG-вопросах записаны, но не подменяют
отдельные невыполненные сценарии.

## Ограничения полного Telegram-пути и памяти

В BotCore перед вызовом pipeline добавляется `[from <имя>]`. Проверенный
instrument_question сопоставляет хеш всего message с шестью исходными вопросами.
В результате штатно оформленный вопрос выходит за план. Это воспроизведено
без сети отдельным regression test. Blob BotCore локально и в серверном base
7eb7b17 совпал: `82d53e88a4d72991fcdbe22d2fc51c495bb3d355`.

Проверка не обходилась удалением префикса или ослаблением хешей. Использован
разрешённый standalone worker с исходными вопросами, его ограниченный охват
указан выше. Исправление привязки должно проверять исходный user_text до
форматирования и сохранять контекст во всех фоновых вызовах. Менять утверждённый
бюджет или принимать произвольный префикс для этого не требуется.

Cgroup worker имеет лимит448МиБ. Два приложения внутри него не запускались.
Прототип такого запуска не использовался. Для последовательной проверки API
и worker использовались отдельные managed запуски. Это не проверка горячих кэшей.
Отдельный `serve channels` предусмотрен оператором, но полный путь через него
требует исправления описанной привязки вопросов. Необходимость увеличивать RAM
этим результатом не установлена, лимиты и серверные права не менялись.
