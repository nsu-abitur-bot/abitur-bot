## 2. Окружение и существующие инструменты

Локальный Docker Desktop недоступен. Запущены новые временные PostgreSQL
и Redis, доступные только на `127.0.0.1:55490` и `127.0.0.1:56390`.
Кластер PostgreSQL создан специально для #390 с пользователем `abitur_390`.
Тесты с `drop_all/create_all` выполнялись только в новой `abitur_390_test`.
Redis проверен через PING; интеграционный тест BotCore использует fakeredis,
чтобы он повторялся и в CI без отдельного Redis. Рабочие БД не использовались.

`tools/latency_full_profile.py` уже умеет снимать тайминги и ограничивать
Gemini SDK attempts, но рассчитан на Gemini, читает настройки и копирует
справочные данные. Его нельзя автоматически применить к смешанному
DeepSeek/Gemini-окружению. `latency_probe.py` вызывает модели и эмбеддинги.
Оба инструмента здесь не запускались. Реальные назначения моделей в настройках
экземпляра не прочитаны. Их нельзя подменять значениями по умолчанию из кода.

В [отчёте #376](../latency-376.md) есть исторические наблюдения другого runtime:
два ответа после изменения конфигурации заняли 31,916 и 24,736 с.
Зафиксированы 13 модельных границ и 6 embedding spans на успешный запрос,
но не все физические HTTP-попытки и повторы. Они не доказывают текущие p95,
частоту ошибок или лимит вызовов. В новых измерениях эта выборка не смешивалась
с локальными прогонами. Сырые рабочие журналы и пользовательские данные не читались.

## 3. Инструменты и методика

- `tools/release_metrics.py` считает p50 как медиану, p95 методом nearest rank, ошибки и
  превышения времени по всем исходам. Неизвестные токены/цены остаются `null`.
  Повторная попытка учитывается отдельным `attempt_id`, дубликаты отклоняются.
  Вопросы, индексация и судья разделены. Валюты не смешиваются.
  Для попытки задаются явные ставки входа/выхода. Скидки за кеш, пакетную
  обработку и другие особенности тарифа автоматически не восстанавливаются.
- `tools/release_offline_probe.py` многократно запускает настоящий код
  `ask_local_llm` через существующие offline-фикстуры. Классификация пути берётся
  из trace FAQ/tools. Поиск, провайдеры и история подменены. Время включает
  ожидание семафора, `service_ms` отдельно показывает выполнение после очереди.
- `tools/release_restore_probe.py` создаёт две новые БД со случайными именами
  в одноразовом локальном кластере. Копирует все таблицы схемы приложения и
  файловый LightRAG с детерминированными моделью, эмбеддингами и токенизатором.
  Старые каталоги не перезаписывает, существующие БД не очищает.
- `tests/postgres/test_release_readiness.py` проверяет HTTP-правку FAQ,
  PostgreSQL NOTIFY, два кеша, настоящий BotCore и пайплайн, форматирование
  каналов, запись вопросов и отзывов. Маршрут FAQ установлен в изолированном
  FastAPI без авторизации. Эмбеддинги и Redis подменены, классификация intent
  отключена. Это не проверка входа сотрудника, UI или доставки мессенджером.

Для будущего живого прогона нужна отдельная фиксация провайдеров и моделей
для Chat, Graph, FAQ embeddings, Graph embeddings и судьи, ревизии настроек,
версии FAQ/KB и тарифов на дату замера. План первой малой серии: по 5 вопросов
на FAQ, RAG и tools, последовательно, без нагрузочного шторма. Это **15 вопросов,
а не 15 платных вызовов**. Число попыток может быть значительно больше.
Индексация и судья получают отдельные бюджеты. До согласования суммы нужен
снимок моделей/тарифов и полный ограничитель попыток для используемых SDK.
При неизвестном учёте повторов денежную верхнюю границу обещать нельзя.
Платные прогоны в этой работе не запускались.

## 4. Выполненные измерения

### Контролируемые прогоны кода

Windows, Python 3.13, 8 offline-сценариев по 20 повторов на каждый уровень
параллельности. Это конечная пачка из 160 одновременно поставленных в очередь
задач, не стационарный поток пользователей. Инициализация фикстур не входит
во время запросов. Нагрузка на провайдеров, SQL и Telegram/MAX отсутствует.

| Параллельность | FAQ / RAG / tools | Ошибок по техническим проверкам | p50 с очередью | p95 с очередью |
|---|---|---:|---:|---:|
| 1 | 60 / 80 / 20 | 0 из 160 | 44,35 мс | 79,58 мс |
| 4 | 60 / 80 / 20 | 0 из 160 | 38,71 мс | 67,64 мс |

Результаты находятся в `release-390-data/offline-c1.json` и `offline-c4.json`.
Успех означает прохождение технических assertions, включая ожидаемый fallback
при искусственном сбое ранжировщика. Это не частота ошибок реального сервиса
и не качество ответов абитуриентам. Эти миллисекунды нельзя сравнивать с живым
требованием 30 секунд или использовать для выбора лимита пользователей.
Токены, attempts и стоимость в отчётах оставлены неизвестными.

### Восстановление пары SQL/LightRAG

Результат одного прогона: `release-390-data/restore.json`.

| Показатель | Результат |
|---|---:|
| SQL-дамп | 47 169 байт, 20 таблиц, включая контрольную |
| LightRAG | 6 809 байт, 7 файлов |
| Восстановление SQL | 214,93 мс |
| SQL и копирование файлов | 221,28 мс |
| До успешной проверки SQL и векторного поиска | 1 404,38 мс |
| Возраст контрольной копии на начало восстановления | 1,491 с |
| Контрольные пары до / после восстановления | 2 / 1 |

На время копии записи остановлены: одноразовый процесс LightRAG завершил
сохранение. SHA-256 всех 7 файлов совпали сразу после копирования. В новом
процессе восстановленный индекс нашёл контрольный текст. Второй документ
и SQL-маркер созданы после копии и в восстановлении отсутствуют. Это проверка
потери одной специально созданной пары после выбранного checkpoint.
Она не определяет худший RPO рабочего сервиса или расписание резервирования.

Содержимое синтетическое, граф сущностей пуст, проверен naive-векторный поиск.
Модели и эмбеддинги локальные детерминированные, ключи провайдеров не нужны.
Размеры и условия слишком малы для вывода о рабочих RTO 4 часа/RPO сутки.
Восстановление не включает получение доступа, загрузку копии с удалённого
хранилища, секреты, запуск ботов и проверку через мессенджеры.

### Доступность, токены и стоимость

Сквозных проб Telegram/MAX за полный период не предоставлено и не найдено
в просмотренных документах. Доступность каждого канала остаётся неизвестной.
Отсутствие истории не считается нулём ошибок или 100% доступности.

Живые токены и стоимость не измерены. Существующий usage финальной генерации
не является полным расходом вопроса: нужны также intent, CRAG, Graph, embedding,
retry и вызванная вопросом фоновая работа. Новый калькулятор принимает только
явные числовые записи, сам их из production не собирает. Порог в 3 вызова,
RTO 4 часа и RPO сутки не подтверждены этим отчётом и не используются как
пройденные критерии. Редактура этих требований остаётся в #391.

обратной связи, FAQ refresh и usage. Добавлены 5 проверок расчётов метрик и

В новой проверке HTTP PUT до применения в двух кешах занял **79,41 мс**.

новый текст FAQ. SQL содержит 2 записи пользователей, 2 входных вопроса

## Повторение и ограничения

Запускать из backend с `PYTHON_DOTENV_DISABLED=1`, `UV_NO_ENV_FILE=1`.
Для новых локальных тестов задать только собственные тестовые значения.
Не использовать имеющиеся production URL или тестовую БД по одному лишь имени.

```powershell
uv run --no-sync python -m tools.release_offline_probe --repeats 20 --concurrency 1 --report offline-c1.json
uv run --no-sync python -m tools.release_offline_probe --repeats 20 --concurrency 4 --report offline-c4.json
uv run --no-sync python -m pytest tests/test_release_metrics.py -q
```

Для SQL-тестов нужен новый отдельный PostgreSQL. В выполненной проверке это
локальный кластер #390 на порту 55490, пользователь `abitur_390`,
`TEST_DB_NAME=abitur_390_test`, все DB_* и DATABASE_URL заданы явно.
Фикстура тестов удаляет и создаёт таблицы только в этой базе.

```powershell
uv run --no-sync python -m pytest tests/postgres/test_release_readiness.py -q -o junit_family=legacy
uv run --no-sync python -m tools.release_restore_probe --pg-bin 'C:/Program Files/PostgreSQL/18/bin' --port 55490 --workdir ../.work/390-local/new-restore-run
```

Последняя команда требует уже запущенный одноразовый кластер. Каталог запуска
должен быть новым. CLI принудительно использует loopback, высокий порт и
тестового пользователя. Он не запускает рабочие службы и не делает backup
рабочих данных. Для Linux используется каталог его собственных pg_* утилит.

Ruff и целевой Pyrefly прошли. Локальные результаты не заменяют CI на HEAD PR.
Общий целевой запуск: 57 тестов успешно за 20,14 с. При очистке подключений
есть RuntimeWarning о не дождавшейся coroutine `Connection._cancel`, который
наблюдался и до новых тестов в отдельном запуске 51 существующей проверки.
В новой интеграционной проверке отдельно он не воспроизвёлся. Также Pyrefly
сообщает о прежних лишних ключах venv-конфигурации. Эти предупреждения не
приравниваются к отсутствию проблем очистки ресурсов.
Хеши исходных числовых файлов, версия Python/ОС и база кода находятся в
`release-390-data/manifest.json`. Время записано с UTC или явным смещением.
Секретные файлы, приватные ключи, рабочие журналы и дампы не читались.
Копии в проверке созданы из собственных новых синтетических данных.

Для завершения оставшихся проверок пунктов 4-5 нужны отдельный наполненный
стенд, фактические назначения моделей, согласованный бюджет, тестовые получатели
Telegram/MAX и история проб доступности. Вопросы качества ожидают #388.
Новые численные требования не предлагаются и не согласуются в этой части.
Wiki и рабочие сервисы не менялись. #390 остаётся открытой и требует ревью.
После проверок оба временных сервера #390 остановлены, порты освобождены.
