согласованный план. Для одного последовательного пилота действуют пределы:

В `cloudru-ready-20261120.md` зафиксированы новый PG15 seed, пересчёт БЗ и FAQ
на Cloud.ru/2048, сохранение старого индекса и резервных копий. Оба селектора
embedding используют Cloud.ru. Tokenizer сверялся с фактическим usage.
[Проверка нового prepare](release-470-data/cloudru-index-verification-after-prepare-20261120.json).

Операторская диагностика и пересчёт стоили по usage 4,820876 ₽ из отдельного
предела 10 ₽, 172 физических запроса. Это не расход пилота и не банковская
сверка. [Отдельный учёт](release-470-data/cloudru-operator-accounting-20261120.json).
Повторять пересчёт не требуется. PG17 primary/restore остались со старым seed,
для будущих измерений используются только PG15 source/target.

## Что проверено 21 ноября

Через ограниченный runner выполнен новый read-only probe исходного PG15 seed.
Он не импортирует приложение, не обращается к сети и не читает секреты.
Хеш файла 82 чанков совпал с проверенным оператором, SHA256 публичного tokenizer
тоже совпал. В трёх чанках есть упоминания профилей, в девяти - языков
программирования. Это проверка наличия тем, не подтверждение ответов бота.
Минимум доступной памяти составил 1372,9 МиБ, проверка заняла 1,504 с.
[Результат](release-470-data/seed-readonly-preflight-2026-11-21.json).

Зафиксирован [окончательный план шести вопросов](release-470-data/pilot-plan-approved-2026-11-21.json)
для run `7d86f895-1cde-4795-aedf-db47b855b674`. В нём шесть уникальных хешей,
денежные и токенные пределы, ревизия и SHA256 tokenizer. Дополнительные вопросы
не допускаются. Генератор плана не создавал серверный бюджет.

`78531e1d41ba70bd16dc4a5823974261d598910d51fef569fd8eb384589baf58`.
Файл `/reports/release470-budget.sqlite3` общий для API/bot/worker. Инициализатор

проверяются шесть вопросов, их хеши, предел 1 ₽ и файл tokenizer.
Платных вызовов и отправки сообщений при этой операции нет.
[Квитанция инициализации](release-470-data/pilot-budget-initialization-2026-11-21.json).

Новые инструменты прошли Ruff, форматирование и целевой Pyrefly. Локально
выполнены 46 unittest: 43 успешны, три Linux-only пропущены по платформе.
Новые регрессии проверяют отказ при подмене вопроса, повышении денежного предела
и использовании несогласованного предложения вместо разрешённого плана.

## Следующий запуск

Provider egress остаётся закрытым. Runner требует операторскую отметку разрешения,
а режим `run pilot` по-прежнему отклоняется. Эти проверки не обходились.
Марату передаются разрешение пользователя, текущая версия ограничителя, план
и лимиты для точечного открытия API и указания разрешённых команд запуска.
После завершения или остановки оператор закрывает подключения.

Чтобы не тратить вопросы повторно, планируется следующий порядок:

1. Один RAG-вопрос (`rag-1`) на исходном PG15, с фиксацией фактического пути.
2. Контрольная отметка before, согласованный snapshot, отметка after, затем
   объявление сбоя и восстановление в независимый пустой target.
3. Второй RAG-вопрос (`rag-2`) на восстановленной цели. Для полного RTO конечная
   точка - приём Bot API последней части полного ответа со штатным поиском.
   Все ожидания после объявления сбоя входят во время восстановления.
4. Два FAQ-вопроса до и после правки одной временной записи через API, с проверкой
   кэша отдельного bot процесса. Два tools-вопроса с фактическими вызовами
   get_education_programs и get_admission_scores.
5. Сверка бюджета и резервов, остановка только тестовых процессов, закрытие API
   оператором, сохранение результатов. Существующие проверки ролей и агрегаты
   повторно не выполняются без причины.

Сбой и восстановление до открытия API не начинались: ожидание подготовки
оператора не должно искусственно увеличивать будущий RTO. SQL и индекс не менялись
новым probe или инициализацией бюджета. Рабочие стенды и #388 сохранены.
