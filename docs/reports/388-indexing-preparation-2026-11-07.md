## Текущее состояние после предоставления доступа

После повторного аудита доработаны предохранители пилота. Неизвестные адреса,
порты, схемы и операции HTTPX запрещены до отправки. Перенаправления провайдеров
не выполняются. Без счётчика разрешены только три точных маршрута локального
API через ASGITransport, с обычной авторизацией.

Для DeepSeek проверяются наличие и сумма input/output/total, а при наличии
кэшированных токенов также их согласованность. Для эмбеддингов проверяется
полнота usage и размер возвращённого пакета. Неполный usage останавливает
последующие вызовы. Искусственные ответы с неполным usage и неизвестными
адресами воспроизвели девять падений до правки, после правки проходят.

Проверки границ в индексаторе заменены с assert на явные исключения.
Они работают и при `python -O`. До входа создаются эксклюзивные файлы-маркеры
попытки, поэтому прерванный запуск не должен автоматически повториться.

`deploy/evals/388/run-one.sh` требует `--execute` и отдельного разрешения
на передачу тестовой учётной записи через stdin. Файлы паролей он не читает.
Он отказывается использовать уже существующие контейнеры, удерживает блокировку
пилота, ограничивает длительность команды и вызывает stop для своего with-kb
при обычном завершении, ошибке запуска/индексации и обрабатываемых сигналах.
Ошибка stop не скрывается. SIGKILL и отключение сервера обработать trap не может:
в таком случае нужно вручную проверить состояние перед следующей попыткой.
Команды reset и запуск empty-kb в этом сценарии отсутствуют.

Индексация после этих изменений также не запускалась. Общая очередь GigaChat
и нагрузка общего сервера остаются эксплуатационными ограничениями, а резерв
5 CNY остаётся расчётным предохранителем, не лимитом списания у провайдера.

Оба тестовых варианта запущены и проверены последовательно через
`sudo -n /usr/local/sbin/abitur-eval388`. Это root-owned wrapper только
для двух проектов #388. Общий доступ к Docker и sudo не выдавался.
При остановке использовался `stop`, тома сохранялись. `reset` не применялся.

Образ: `ghcr.io/nsu-abitur-bot/abitur-bot@sha256:9f6278952bc3bef2635d21c33d7dee983befaf801294c17c014686dead210f4e`.
Версия приложения: `0ec0f788cf590b364e9e7a65f2f0c53de4d5bf40`.

## Что проверено на сервере

Подключение: `mihail@nsu.abitur.site:22`. Ключ сервера ED25519 сверялся с
отпечатком, полученным от пользователя, при каждом SSH-вызове:

Проверки выполнялись без пересылки SSH-agent и портов.

Прочитаны только несекретные файлы:

- `/usr/local/bin/abitur-nsu-compose`
- `/opt/abitur/backend/deploy/demo/compose.yaml`
- `/opt/abitur/backend/deploy/demo/runtime.yaml`

Wrapper НГУ использует эти compose-файлы, отдельный файл конфигурации
`/etc/abitur-instances/nsu.env` и `/opt/abitur/images.yaml`.
Содержимое env не читалось. Файл закреплённых образов не был доступен
для чтения. Фактические image digest и SHA работающего приложения
не установлены.

В прочитанной конфигурации LightRAG работает в файловом режиме:
`LIGHTRAG_STORAGE=json`, путь `/app/data/lightrag`, volume `files`.
PostgreSQL хранит прикладные данные, Redis выделен отдельным сервисом.
Runtime overlay задаёт общий volume блокировок GigaChat
`abitur-provider-locks`. Это средство ограничения параллельных обращений
к провайдеру, его нельзя игнорировать при будущем тестовом запуске
с тем же аккаунтом. Документы и базы университетов в нём не хранятся.

Это проверка файлов развёртывания. Значения из работающих контейнеров,
настройки моделей в БД и соответствие им конфигурации ещё не проверены.
Назначения GigaChat/DeepSeek/Gemini известны со слов пользователя.

Через `ss -ltn` установлены loopback-порты API 18001-18003 и web 13001-13003.
Наличие порта не доказывает исправность приложения. Новые порты не открывались.
После подготовки файлов все три API ответили HTTP 200 на GET `/openapi.json`,
все три web ответили HTTP 200 на GET `/`. Это проверка доступности этих
страниц, а не полноценная проверка ботов, поиска или ответов моделей.
При первом осмотре доступно около 1266 МиБ RAM, swap уже использовался.
Ресурсную нагрузку новых контейнеров проверить пока нельзя.

## Почему индексация не выполнена

`docker ps` вернул отказ доступа к `/var/run/docker.sock`.
`sudo -n -l` сообщил, что пользователю `mihail` запрещено использовать sudo.
Права и настройки сервера не менялись, обхода ограничений не было.

Поэтому документ только передан в отдельный каталог, в граф он не загружен.
Вызовов моделей и расходов нет. Фактическую цену индексации и оставшихся
восьми документов сейчас определить нельзя.

Для продолжения нужен администратор сервера: проверить существующие
контейнеры и подготовить отдельный ограниченный запуск. Выдавать полный
доступ ко всем Docker-контейнерам ради этой задачи необязательно.
Существующие стенды не останавливать и не перезапускать.

Перед платным запуском нужно проверить учёт usage на уровне фактических
HTTP-попыток. Адаптер LightRAG DeepSeek возвращает только текст, а адаптер
эмбеддингов GigaChat возвращает только векторы. Их обычные результаты не
сохраняют полный расход индексации. Счётчик должен учитывать входные и
выходные токены, кэш DeepSeek, повторы и частичные ошибки. Недоступные
данные помечаются неизвестными. HTML-документ не требует Gemini для PDF.

## Как проверить вручную

```sh
ssh mihail@nsu.abitur.site
cd /home/mihail/abitur-evals/388-20261107
cat README.md
sh verify-preparation.sh
cat manifest.json
find with-kb empty-kb -type f
```

Последняя команда должна ничего не вывести. Проверка сверяет контрольные
суммы, отсутствие символьных ссылок и пустоту обоих деревьев. Она не
запускает контейнеры, не вызывает модели и не меняет демостенды.

валидатор набора, Ruff по изменённому тесту и `git diff --check`.
В тестах подключения к внешним моделям и общим хранилищам не было.
