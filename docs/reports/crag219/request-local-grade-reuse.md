# Повторные оценки CRAG: сравнение 11 ноября 2026

Работа по #219. Повторный retrieval после переформулировки может вернуть уже
оценённый текст. Раньше он отправлялся оценщику заново с теми же вопросом,
историей и инструкцией. Теперь успешный результат переиспользуется внутри
одного `run_crag`. Ошибки/невалидные оценки повторяются; следующий вопрос
получает отдельный кеш. Проверки релевантности и промпты не отключались.

## Измеренный эффект

Один парный запуск CRAG на реальных публичных фрагментах НГУ с реальным
DeepSeek. Начальный набор — 11 фрагментов, повторный — эти же 11 плюс ещё один
из страницы абитуриента ФИТ. В наборе есть повторяющийся текст; поэтому число
уникальных prompt меньше числа возвращённых фрагментов. Использована обычная
конфигурация CRAG, без снижения порогов или лимитов проверок.

| Метрика | До (`38a4d2c`) | После |
| --- | ---: | ---: |
| Полное время CRAG | 7,589 с | 4,566 с |
| Логические текстовые вызовы | 24 | 12 |
| Фактические HTTP-попытки | 24 | 12 |
| Оценки фрагментов | 23 | 11 |
| Переформулировки | 1 | 1 |
| Повторные retrieval | 1 | 1 |
| Входные токены | 15035 | 7234 |
| Выходные токены | 298 | 166 |
| Ошибки провайдера | 0 | 0 |

Упорядоченные хеши оставленных фрагментов совпали полностью, включая дубли.
Дедупликация выдачи не входит в эту правку. В детерминированном регрессионном
сценарии положительная и отрицательная оценки переиспользуются: пять оценок
превращаются в три, содержимое результата сохраняется.

[Публичный вход](public-input.json) содержит реальные тексты и справочник,
выбранную модель и профиль; API-ключа в нём нет.
[Результат](component-result.json) содержит хеши исходников/входа/промптов,
поэтапное время транспорта, число HTTP-попыток и токены. Заголовки, ключи,
история пользователей и ответы пользователей не записываются.

## Границы измерения

Это компонентный опыт с фиксированной выдачей retrieval, а не измерение
сквозного Telegram/MAX или всего LightRAG. Здесь нет живого векторного поиска,
эмбеддингов и доставки. Нельзя вычитать полученную разницу из задержки любого
ответа бота или заявлять p95/SLA по этой паре.

Обе ветви запускались последовательно в одном процессе и использовали один
HTTP-клиент: первая ветвь включала установку соединений, вторая могла получить
тёплые соединения и серверный кеш провайдера. Поэтому причинно подтверждено
сокращение числа запросов; точное ускорение требует более широкой выборки.

`receive_response_headers` включает ожидание провайдера и сеть — это не чистая
сетевая задержка. Суммы параллельных вызовов не являются полным временем CRAG.
Провайдер не раскрывает отдельно очередь и вычисление, эти величины здесь
не придуманы. Это не отчёт о цене: токены записаны, денежный расход не рассчитан.

## Воспроизведение

1. Создать отдельную **свежую** PostgreSQL БД с именем `crag219_*` и направить
   `DATABASE_URL` только на неё. Инструмент отказывается от другого имени
   или существующих таблиц; никаких сбросов таблиц он не делает.
2. Сохранить старый CRAG: `git show 38a4d2c:rag/crag.py > /tmp/crag219-before.py`.
   `--baseline` исполняет указанный локальный Python-файл: это должен быть
   проверенный исходник, а не непроверенный файл из сети.
3. Передать `public-input.json` через приватный stdin, добавив в `settings`
   разрешённый `DEEPSEEK_API_KEY` из менеджера секретов/окружения. Не записывать
   ключ в исходники, аргументы CLI или отчёт. `PYTHON_DOTENV_DISABLED=1` исключает
   случайное чтение локальных настроек проекта.
4. Запустить `uv run python tools/benchmark_crag_reuse.py --execute
   --baseline /tmp/crag219-before.py --output /tmp/crag219-result.json
   --repeats 1 --attempt-limit 40`. Это платный opt-in запуск: в данном опыте
   суммарно выполнено 36 HTTP-попыток. Прерывание по лимиту/ошибка делают
   сравнение неуспешным; оно не выдаётся за успешное ускорение.
5. Сравнить `kept_sha256`, ошибки, токены и количество попыток в обоих плечах.
   Для повторения требуется новая свежая БД и новый путь отчёта. Секретный stdin
   не сохраняется; файл результата создаётся с правами `0600` и без перезаписи.

Автоматические регрессии: `uv run pytest tests/rag/test_crag.py` на отдельной
тестовой PostgreSQL БД. Проверены корректный/невалидный результат, временная
ошибка, повторный вопрос и одновременно выполняемые одинаковые вопросы.
Следующий этап #219 — сквозная выборка на живой наполненной БЗ после отдельного
решения о внедрении. Этот PR не выкладывает изменения и не объявляет задачу
полностью принятой.
