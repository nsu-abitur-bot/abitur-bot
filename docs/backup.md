# Резервное копирование БД и базы знаний

Автоматический бэкап (#229) снимает два главных актива проекта:

- **PostgreSQL** — пользователи, FAQ, документы, настройки, конкурсные списки;
- **файловую базу знаний LightRAG** — `data/lightrag/`: граф (`*.graphml`),
  векторный индекс (`vdb_*.json`) и kv-хранилища (`kv_store_*.json`). Их нет
  в базе, обычный дамп БД их не покрывает.

## Как устроено

Сервис `backup` в `docker-compose.yml` крутит `python -m tools.backup`:
каждые `BACKUP_INTERVAL_SECONDS` (по умолчанию сутки) он снимает слепок в
`./backups/abitur-ГГГГММДД-ЧЧММСС/`:

- `postgres.dump` — согласованный дамп `pg_dump -Fc`;
- `lightrag.tar.gz` — архив `data/lightrag/`;
- `manifest.json` — время, размеры и число файлов (для проверки полноты).

Слепок собирается во временном каталоге с точкой в имени и получает финальное
имя только после успеха — оборванный бэкап нельзя перепутать с полным.
Ротация держит последние `BACKUP_KEEP` слепков (по умолчанию 14), старые
удаляет.

Настройки — в `.env` (`BACKUP_INTERVAL_SECONDS`, `BACKUP_KEEP`, `BACKUP_DIR`).
`./backups` живёт на хосте рядом с `data/` — на другой диск/в облако её можно
синхронизировать любым внешним rsync/borg; в compose она не публикуется.

## Ограничения

- Дамп PostgreSQL транзакционно-согласован сам по себе. Архив LightRAG
  снимается на живом каталоге: файл, который бот писал в момент копирования,
  может попасть в архив неполным. На практике индекс пишется редко
  (индексация документов), поэтому ночной слепок достаточно надёжен; полную
  гарантию даёт снятие слепка при остановленном боте.
- Проверить целостность слепка на стенде можно `tools/release_restore_probe.py`
  (хеши файлов и восстановление пары SQL/БЗ).

## Восстановление (откат)

```sh
docker compose stop bot api scheduler   # кто пишет в БД и БЗ должен молчать
ls backups/                              # выбрать слепок

# ./data в сервисе backup смонтирован только на чтение (безопасность),
# поэтому на время восстановления перемонтируем его с правом записи.
docker compose run --rm -v "$(pwd)/data:/app/data" backup \
  python -m tools.restore backups/abitur-20261109-030000
docker compose up -d
```

`tools.restore` разворачивает дамп (`pg_restore --clean --if-exists` — объекты
пересоздаются) и распаковывает базу знаний. Текущий каталог БЗ не удаляется,
а отодвигается в `data/lightrag.pre-restore-<время>` — если восстановление
оказалось ошибкой, прежнее состояние ещё на месте. Спросит подтверждение;
`--yes` — без вопросов, `--no-db`/`--no-kb` — восстановить только одну часть.

## Переезд на другой сервер

1. На старом сервере: `docker compose run --rm backup python -m tools.backup --once`,
   затем перенести `./backups/` (последний слепок) и `.env` на новый сервер.
2. На новом: развернуть репозиторий, положить `.env`, поднять стек
   (`docker compose up -d`) — миграции применятся к пустой базе, затем
   остановить процессы и выполнить восстановление как выше.
3. Проверить: `docker compose ps` — все сервисы healthy, бот отвечает,
   поиск по базе знаний работает.

## Ручной слепок без ожидания цикла

```sh
docker compose run --rm backup python -m tools.backup --once
```
