# Алерт: восстановление за 15 минут

Регламент для любого доступного участника команды. Летнего дежурства и обещания
круглосуточной реакции нет. 15 минут — целевое время восстановления **с момента,
когда участник взял инцидент**, которое нужно подтвердить учебной проверкой.

## 0–2 минуты: взять инцидент и определить стенд

Ответить получателям алерта «разбираюсь». В сообщении есть имя стенда, причина и
ссылка сюда. Нужны заранее выданные SSH-доступ к `myserver`, право запускать
Compose-wrapper и доступ администратора нужного стенда. Не пересылать ключи в чат.
Если доступа нет — сразу подключить доступного участника с доступом.

```sh
ssh myserver
# Выбрать имя из алерта; посмотреть доступные wrappers:
ls /usr/local/bin/abitur-*-compose
# Ниже пример для nsu; для другого стенда заменить имя wrapper.
sudo /usr/local/bin/abitur-nsu-compose ps --all
sudo /usr/local/bin/abitur-nsu-compose logs --since 10m --tail 100 api bot
```

Не публиковать полные логи: там могут быть вопросы пользователей и другие данные.
Если SSH не отвечает — проверить сервер в панели хостинга: питание, сеть, диск.
Не перезагружать хост вслепую: это затронет все стенды.

## 2–7 минут: устранить типовую причину

| Признак | Действие |
|---|---|
| Один процесс остановлен или завис | `sudo /usr/local/bin/abitur-nsu-compose up -d --no-deps api` для отсутствующего/остановленного API; `restart api` для зависшего. Аналогично `bot`, `web`, `scheduler`, только если сервис предусмотрен этим стендом. |
| Ошибки подключения к Redis/PostgreSQL | Проверить `ps --all`, затем `logs --since 10m --tail 100 redis postgres`. Восстановить остановленный сервис через `up -d redis` или `up -d postgres`; при повторном падении проверить диск (`df -h`) и память (`free -m`). |
| 429/квота/401 провайдера | В админке проверить баланс и ключ настроенного провайдера. Исправить ключ/пополнить квоту уполномоченным участником. Перезапуск не лечит квоту; не менять эмбеддер существующей базы. |
| TelegramConflictError | Найти второй polling-процесс того же бота; остановить старый экземпляр. Не запускать второй процесс с тем же токеном. |
| Ошибки начались сразу после обновления | Проверить результат Actions и `/opt/abitur/deploy-failure.json`. Использовать откат приложения по [инструкции деплоя](../deploy/ci/README.md#retry-and-manual-application-rollback), под общей блокировкой деплоя; не откатывать БД. |

Нельзя выполнять `down -v`, удалять тома/БД/индекс, делать blanket prune или
восстанавливать backup поверх живой базы ради быстрого снятия алерта.

## 7–12 минут: проверить восстановление

1. `ps --all`: нужные процессы running, healthcheck healthy, нет цикла рестартов.
2. Открыть админку, войти; задать боту простой вопрос и получить ответ.
3. Проверить новые ошибки в логах. Ошибочный пятиминутный интервал должен истечь,
   после чего монитор отправит RESOLVED. Сообщение означает успешные технические
   проверки, а не гарантию правильности всех ответов.

## 12–15 минут: зафиксировать результат

Сообщить «восстановлено», стенд, причину, действие, время от принятия инцидента.
Если не починилось — передать доступному участнику симптомы и уже выполненные
действия; не продолжать разрушительные эксперименты. Завести задачу на причину.

## Приёмка (заполняется фактическими результатами)

Другой участник, не автор мониторинга, проходит регламент на согласованном
демостенде. Не останавливать рабочие стенды без согласованного окна.

- Тест доставки: `--test`, оба получателя подтверждают сообщение.
- Падение: остановить один согласованный сервис; получить ALERT, восстановить
  по регламенту, получить RESOLVED и успешный ответ бота.
- Рост ошибок: на отдельном тестовом Compose-проекте вывести минимум 5 записей
  `ERROR` за 5 минут; получить ALERT, прекратить генерацию, получить RESOLVED.
- Недоступный сервер: направить тестовую цель монитора на недоступный SSH-хост;
  убедиться, что уведомление приходит с отдельного сервера мониторинга.
- Записать дату, стенд, оператора, время сбоя/алерта/начала ремонта/ответа бота,
  ссылки на сообщения и длительность. Цель: ремонт ≤15 минут.
