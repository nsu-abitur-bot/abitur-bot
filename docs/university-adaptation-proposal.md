# Адаптация экземпляра под другой вуз — предложение для согласования

Статус: параметризация согласована пользователем в чате перед реализацией.
Реализованные параметры и ограничения описаны в university-settings.md.
Материалы целевого вуза и live-приёмка остаются за командой.

## Параметры в БД через существующий каталог #356

Группа «Вуз»: UNIVERSITY_SHORT_NAME, UNIVERSITY_FULL_NAME, ASSISTANT_NAME,
UNIVERSITY_WEBSITE, ADMISSIONS_EMAIL, ADMISSIONS_PHONE, ADMISSIONS_ADDRESS,
UNIVERSITY_LOGO_URL. Пустые контакты не выводятся. Для URL — существующая
валидация URL; текстовые поля ограничиваются по длине. Контакты — реквизиты
интерфейса, а не разрешение модели выдумывать информацию или ссылки.

UNIVERSITY_PROFILE: nsu / custom. У существующего экземпляра сохраняется nsu.
Новый демостенд команды переключают в custom через админку до запуска
каналов и загрузки материалов. Инфраструктурный старт демо выполняет только
миграции; обычный bootstrap должен учитывать профиль до запуска сидов.
При custom блокируются сиды справочника/баллов НГУ и специфичные парсеры даже
при оставшихся включённых SEED_* и SCHEDULER_ENABLED. Возврат в nsu не удаляет
материалы; смена профиля не является очисткой БД.

## Изменения промпта на согласование

SYSTEM_PROMPT_VERSION: 1.0 → 2.0 (роль теперь зависит от экземпляра).
В SYSTEM_PROMPT_BASE предлагается заменить только реквизиты:

- «помощник-бот для абитуриентов НГУ (Новосибирский государственный университет)»
  → «{assistant_name} для абитуриентов {university_short_name}
  ({university_full_name})»; дефолт имени — «официальный дружелюбный помощник-бот».
- Все остальные вхождения «НГУ» → подстановка university_short_name, включая
  границу тематики, заголовок контекста и текст отказа.
- Имя, полное и краткое названия подставляются как значения format, не как
  произвольный шаблон промпта. Произвольный редактор промпта не добавляется.
- Правила 1–6, требование брать баллы только из инструмента, правила источников,
  запрет выдумывания и HTML-форматирование остаются прежними.
- На nsu с дефолтами итоговый текст должен совпасть с текущим посимвольно.
- Другие промпты меняются только при обнаружении реквизитов НГУ; каждое такое
  изменение также требует фиксации версии и проверки рендеринга nsu.

## Найденные точки привязки и план обработки

| Точка | Решение |
| --- | --- |
| pipeline/prompts.py | Подстановки реквизитов после согласования |
| bootstrap/seed.py | Запрет справочника/баллов НГУ при custom |
| config/instance.py | Новые поля в каталоге БД и существующем редакторе #356 |
| scheduler/main.py, parser/ | Запрет специфичных сервисов при custom |
| FAQ/сокращения из локальных YAML | Не загружать локальные материалы НГУ при custom |
| abitur-web: abbrev-form.vue, rag-parser.vue | Нейтральные примеры вместо НГУ/nsu.ru |
| abitur-web: rating.vue, server/api/rating.get.ts | Скрыть неадаптированный рейтинг и фиктивные данные при custom |
| Логотип и реквизиты UI | Данные текущего экземпляра, без общего каталога организаций |

Это карта известных точек по первоначальному поиску; при реализации проверяется
также весь путь подготовки контекста, инструмент баллов и пользовательские ошибки.

## Приёмка

Падающие тесты до исправлений для попадания сидов/локальных FAQ в custom;
проверки каталога настроек и прав. Регрессионный рендер nsu. В эталонном YAML —
сценарий второго вуза с отдельным контекстом и источником, без присвоения
синтетическому ответу статуса экспертно проверенного. Живая проверка по
материалам команды оформляется отдельно; фикстуры не заменяют её.

Два отдельных экземпляра должны показывать свои реквизиты, не получать данные
НГУ автоматически и возвращать источники соответствующего вуза. Проверяются
не только выключенные настройки, но и защитный отказ при попытке включить
специфичный сервис НГУ в профиле custom.
