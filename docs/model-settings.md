# Два назначения моделей и пересчёт индексов

В «Подключения → Модели» администратор выбирает текстовую модель и модель
эмбеддингов. Текстовая модель используется для ответов, CRAG, графа, подготовки
текста и заголовков. FAQ и LightRAG используют один embedding-клиент с одним
контрактом запроса и фактически проверенной размерностью.

Общие ключи и адрес подключения вводятся один раз. Неиспользуемые подключения
сохраняются в зашифрованном снимке и скрываются из основной формы. Технические
профили этапов остаются с прежними дефолтами; промпты и пороги не изменены.

## Существующие настройки

До явного сохранения новая версия продолжает читать прежние пять назначений.
Форма показывает их до перехода. `TEXT_PROVIDER/TEXT_MODEL` и
`EMBEDDING_PROVIDER/EMBEDDING_MODEL` проецируются на прежние ключи потребителей
при сохранении; `_model_settings_version=2` обозначает явный переход.
Старый API после перехода не позволяет вернуть несовместимые независимые
назначения. Внутренние метаданные поколения не принимаются как поля формы.

Первый переход на единый контракт требует пересчёта наполненной базы даже
при совпадающих названиях и размерности. Например, legacy Gemini graph и FAQ
посылали разные параметры `task_type`; одинаковая длина вектора не доказывает
совместимость. При последующих изменениях сравниваются провайдер, модель,
endpoint и фактическая размерность. Одна ротация ключа не меняет пространство.
На пустой установке выполняется проверка подключения без обхода документов.

Распознавание сканов — отдельное необязательное подключение OpenAI/Gemini.
Его прежний выбор сохраняется, ключ не дублируется, если это уже выбранное
подключение. DeepSeek не получает изображения. Полный текстовый слой PDF
читается локально с ограничением страниц; смешанный PDF со страницей без
текста и с изображениями/графикой требует распознавания. Отсутствующее или
выключенное распознавание сообщает понятную ошибку вместо скрытого обращения
к другому платному провайдеру. Поддерживаемые расширения загрузки прежние.

## Фоновое задание

`POST /api/v1/settings/instance/models` принимает `revision`, `changes` и
`confirm_reindex`. Проверяются текстовая модель, новый embedder и реальная
размерность. Если нужен пересчёт, требуется явное согласие на платные вызовы.
Повтор уже принятого сохранения возвращает то же активное задание.

Журнал хранится в PostgreSQL, в существующей таблице `settings`:
`model_migration:<id>` и указатель `model_migration_active`. Целевой снимок
внутри задания целиком зашифрован тем же мастер-ключом. Публичный ответ содержит
статус, прогресс, общие названия целевых моделей и безопасную ошибку.

Состояния: `queued → running → completed`; ошибки дают `failed`, отмена проходит
через `cancelling → cancelled`. Кнопки продолжения/отмены используют
`POST /api/v1/settings/instance/models/job/<id>/retry|cancel`. Устаревшая
ревизия и заменённое новым задание не активируются. `GET .../models` возвращает
единый согласованный снимок формы и состояние задания, без секретов.

API запускает один worker под файловым lock. Журнал, исходный снимок,
рассчитанные пакеты и новое поколение переживают перезапуск контейнера:

- `<LIGHTRAG_WORKSPACE_BASE>/.migration-jobs/<id>/` — копия исходных данных,
  FAQ и checkpoints завершённых embedding-вызовов;
- `.generations/<id>/` — подготовленные графы/векторы, FAQ-кеш и признак готовности;
- `.model-migration.json` — временная блокировка записей;
- `.model-generation.json` — опубликованный номер поколения для защиты от
  записи старым процессом до обновления его снимка.

Эти файлы должны находиться на том же **общем постоянном томе**, который уже
используют API и боты для LightRAG. Worker и файловый fence рассчитаны на Linux
и macOS/POSIX. Новые поля `.env` и серверные секреты не требуются.

Очередь загрузки должна завершиться до начала. Во время пересчёта изменения
FAQ/материалов и обычное сохранение настроек получают HTTP 423. Чтение продолжает
использовать старые согласованные настройки и индекс. Старый in-flight вопрос
сохраняет свой снимок до конца, включая параметры заданий постоянных очередей
LightRAG. Провайдеры создаются под thread lock, чтобы параллельные старые запросы
и staging не получили клиент чужого снимка.

Пересчитываются векторы чанков, сущностей, отношений и всех FAQ-вопросов/алиасов.
Граф повторно текстовой моделью не извлекается. Сверяются полнота векторных
хранилищ, исходные тексты и зарегистрированные готовые документы. Исходный
рабочий индекс не перезаписывается. Checkpoints позволяют не отправлять повторно
успешно рассчитанные тексты. При retry канонические данные копируются заново,
поэтому исправления после неуспешного задания не теряются.

В JSON-режиме новое поколение выбирает отдельный корневой каталог. В PostgreSQL
канонические KV/doc-status клонируются в новый `workspace` в транзакции
переключения настроек; векторные файлы/GraphML остаются на томе. Кеш ответов
LightRAG не переносится, кеш векторов популярных вопросов имеет отдельный ключ
поколения. Старые PostgreSQL workspace и файлы сохраняются. Автоматической
очистки старых поколений в этом изменении нет.

После публикации все процессы выбирают пару «настройки + поколение» из снимка.
FAQ нового поколения поднимается из подготовленного кеша, слушатель последующих
изменений обращается к текущему matcher. Старый процесс не может записать
в старый индекс после переключения: до следующего обновления снимка запись
отклоняется. Ошибка/отмена/конфликт сохраняет прежний рабочий индекс.

## Проверки и границы приёмки

На настоящей отдельной PostgreSQL проверяются смена размерности с наполненными
FAQ и документом, вектора всех трёх типов, JSON/PG KV, сохранение источника,
сбой/повтор с checkpoints, отмена, конфликт ревизий и остановка worker во время
ошибки embedding-потока. Регрессия Gemini использует настоящий `GeminiEmbeddings`
и LightRAG queue со stub только на границе SDK; сравнивает параметры staging,
FAQ и live graph, а не только длину синтетических векторов.

Браузерные сценарии проверяют два назначения, скрытие неиспользуемого ключа,
подтверждение пересчёта, блокировку формы, завершение/ошибку/retry и сохранение
черновика при конфликте. Полный браузерный набор выполняется в CI.

Платный живой приёмочный прогон и выкладка на демостенды не выполняются этим PR.
Для них нужен отдельный изолированный стенд с копией реальных материалов,
разрешёнными ключами и общим ограничителем аккаунта GigaChat. Его результат и
расход фиксируются отдельно; автоматического переключения работающих вузов нет.
