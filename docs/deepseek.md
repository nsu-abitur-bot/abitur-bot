# DeepSeek: подключение и переход (#377)

## Реализованный контракт

Проверено по официальной документации 2026-11-01:
[Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/),
[thinking](https://api-docs.deepseek.com/guides/thinking_mode/),
[модели и цены](https://api-docs.deepseek.com/quick_start/pricing/).
Текущая модель по умолчанию — `deepseek-flash`, адрес —
`https://api.deepseek.com`. Адрес и модели чата/графа редактируются независимо.

DeepSeek теперь документирует и Responses API. Этот провайдер использует
отдельный Chat Completions адаптер; совместимость с реализацией OpenAI Responses
не предполагается. Connection check также вызывает `/chat/completions`.
В запросе явно выключен thinking (`thinking.type=disabled`): иначе API включает
его по умолчанию, а его reasoning-история требует другого контракта.
Режим выбран для сохранения текстовой истории и бюджета генерации; качество
именно этого режима нужно оценить до перехода. Промпты не изменены.

Адаптер передаёт system/user/assistant историю, собирает фрагментированные
function calls по индексу, возвращает результаты с `tool_call_id`, стримит текст
через callback и суммирует usage всех раундов. После трёх раундов инструментов
финальный запрос использует `tool_choice=none`. Незавершённые ответы/потоки и
невалидные tool calls завершаются ошибкой. Сырые upstream-ошибки connection
check не попадают в API-ответ. Графовый адаптер сохраняет историю и системный
промпт и использует профиль GRAPH; ошибки не подменяются пустым успехом.

HTTP-contract тесты используют настоящий SDK с синтетическим `MockTransport`.
Это проверка формата запросов/ответов и интеграции, **не live-вызовы DeepSeek**.

## Админка и откат

Существующий schema-driven API настроек публикует группу DeepSeek:
`DEEPSEEK_API_KEY` (Fernet, маскировка), `DEEPSEEK_BASE_URL`, `DEEPSEEK_MODEL`,
`DEEPSEEK_GRAPH_MODEL`, `DEEPSEEK_TEMPERATURE`, `DEEPSEEK_MAX_TOKENS`,
`DEEPSEEK_TIMEOUT_SECONDS`. Повторяемые настройки задаются через админку,
а не новые записи `.env`. Superadmin API, ревизии, проверка перед сохранением
и периодическое обновление снимка остаются прежними.

Назначения `LLM_PROVIDER` и `LIGHTRAG_LLM_PROVIDER` принимают `deepseek`.
Для эмбеддингов FAQ/графа и PDF/vision DeepSeek выбрать нельзя. Их текущие
настройки, размерности и индексы не меняются; для перехода сохранить Gemini
для эмбеддингов и vision. Дефолт PDF в каталоге не изменён: существующее
назначение не следует переписывать вместе с генерацией.
Смена только графовой LLM разрешена при наполненном индексе, смена пространства
эмбеддингов по-прежнему блокируется.

Откат: вернуть `LLM_PROVIDER=gemini` и, если менялся граф,
`LIGHTRAG_LLM_PROVIDER=gemini` через админку. Сохранённый Gemini-ключ не удалять.
Проверка перед сохранением подтверждает доступность Gemini; переиндексация
не нужна. Никакого автоматического переключения стенда этот PR не выполняет.

## Обязательная live-проверка перед переходом

На момент реализации ключ не найден по имени в окружении процесса, локальном
`.env` и сохранённом снимке настроек. Другие API-ключи не использовались.
Live-сравнение, измеренный baseline Gemini и переключение **не выполнены**.
Необходим действительный DeepSeek-ключ и изолированный тестовый экземпляр
с зафиксированными данными. Статический offline baseline не заменяет live baseline.

1. В тестовом экземпляре сохранить ключ через superadmin API. Проверить
   `deepseek:chat` и `deepseek:graph` (при планируемом использовании графа).
   Не менять рабочий стенд, Telegram/MAX и тарифы.
2. Зафиксировать commit, снимок БД/FAQ/источников, параметры CHAT/GRAPH,
   текущие модели и дату. Секреты в отчёт не включать. Использовать один набор:
   `evals/deepseek_scenarios.yaml` плюс весь актуальный `evals/scenarios.yaml`.
   Новый набор содержит баллы через инструмент, смену факультета в истории и
   RAG со ссылками. Это кандидаты, ещё не одобренные экспертом.
3. В отдельных процессах загрузить снимок тестовых настроек, вызвать
   `config.instance.install` и `PipelineEvaluator(...).run()` сначала с Gemini,
   затем с DeepSeek. Между прогонами менять в локальной копии снимка только
   `LLM_PROVIDER`; не писать переключение в общую БД. Сохранять JSON-отчёты,
   ответы и tool trace для одинаковых сценариев. Для изолированной проверки
   графового адаптера отдельно выполнить extraction/query с тем же источником
   во временном workspace; существующие индексы не использовать для вставок.
4. Сравнить с сохранёнными Gemini-ответами и результатами SQL/источниками вручную:
   точность чисел, отсутствие выдуманных фактов, корректный факультет и ссылки,
   сохранение правил отказа и поведения FAQ. Одних regex/assertions недостаточно.
   Не изменять промпты для улучшения результата сравнения.
5. Повторить одинаковые запросы при одинаковой конкуренции, отдельно отметить
   холодный/тёплый кэш. Для скорости использовать замеры задачи #376 (TTFT,
   полная задержка, p50/p95), для стоимости — фактические usage и тариф на дату
   измерения с учётом cache hit/miss и peak/off-peak. Здесь instrumentation
   пайплайна не меняется. Не заявлять выигрыш без измерений.
6. После приемлемого качества и скорости, зелёного CI и отдельной проверки PR
   выполнить переход генерации через админку в согласованном окне. Граф менять
   только после его отдельной live-проверки. Сохранить исходные назначения для
   отката, проверить те же сценарии после переключения.

На дату проверки документации для Flash стоимость за 1M токенов: input cache
miss $0.15/$0.30, cache hit $0.003/$0.006, output $0.60/$1.20 (off-peak/peak).
Это справочные тарифы, а не измеренная стоимость нашего ответа; перед запуском
сверить их снова. Сравнения стоимости с Gemini пока нет.
