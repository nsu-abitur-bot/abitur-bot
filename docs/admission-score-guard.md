# Проверка источника проходных и средних баллов

При уточнении «а средний балл?» модель иногда отвечает, что сведений нет,
потому что в прошлом ответе был только проходной балл. Отсутствие числа в
истории не доказывает его отсутствие в PostgreSQL.

`pipeline/score_guard.py` распознаёт русские вопросы про проходной/средний
балл и короткие уточнения про год, бюджет/платное или уровень образования
в продолжающемся разговоре о баллах. Ветка включена в `_run_tool_loop`,
поэтому действует и при недоступном поиске по документам. FAQ остаётся
самостоятельным источником готовых ответов и этот цикл не проходит.

## Порядок проверки

1. Обычная генерация вызывается без публикации промежуточного текста.
2. Проверяется фактический вызов `get_admission_scores`, его параметры и
   структурированный статус результата. Упоминание инструмента в тексте
   ничего не подтверждает.
3. Если вызова не было либо его параметры противоречат известным фильтрам,
   выполняется одна дополнительная генерация. В ней доступен только этот
   инструмент, его первый вызов обязателен, а известные фильтры закреплены
   в JSON Schema. После получения результата провайдер снова может ответить
   текстом. Поддержаны OpenAI Responses, Gemini и DeepSeek Chat Completions.
4. При успешной проверке публикуется итог. При ошибке SQL или повторном
   пропуске инструмента возвращается «Не удалось проверить баллы…».
   Пустая SQL-выборка имеет отдельный статус `empty` и допускает ответ об
   отсутствии данных. После ошибки SQL дополнительная генерация не запускается.

`AdmissionScoresResult` совместим со строкой для SDK, но отдельно хранит
статус `ok` / `empty` / `error`. Ошибка определяется по статусу, а не по
поиску слов в сообщении. Метрика по умолчанию остаётся `passing`.

## Контекст уточнений

Успешный запрос сохраняет параметры вместе с ответом в истории Redis
(`admission_scores`). Когда SQL вернул единственную программу, год или форму,
сохраняется фактически найденное значение. Это позволяет продолжить разговор
после запроса по алиасу направления или по доступным прошлым годам.
Метаданные остаются внутренними: SDK получает обычный текст сообщений.
Отдельного бессрочного кеша и новой таблицы нет; контекст живёт с историей.

Для старой истории без метаданных восстанавливаются явно названные
пользователем код направления, год, форма, уровень и метрика. Числа и фильтры
из непроверенного текста прошлого ответа не используются как подтверждение SQL.
Смена темы прекращает наследование. Короткое «а средний?» без контекста
вызывает просьбу уточнить направление.

«Какой средний балл?» также считается уточнением, если направление уже задано.
«А на 09.03.04?» меняет код направления, «а по платному?» — форму обучения;
остальные фильтры сохраняются. Без предшествующего разговора о баллах эти
реплики не включают guardrail. Общий вопрос о среднем балле без направления
вызывает уточнение ещё до создания клиента LLM. Повторение такого вопроса
после просьбы уточнить направление не создаёт контекст само по себе.

При смене уровня образования прежний код программы сбрасывается. Если новый
код не назван, бот уточняет направление вместо запроса несовместимой пары
«код бакалавриата + магистратура». После уточнения новый код используется
с выбранным уровнем.

Для сравнения нескольких лет или форм обучения требуется полная выборка
без фильтра по сравниваемому полю. Отдельный запрос только за 2023 год не
покрывает вопрос про 2023 и 2024; запрос только на бюджет не покрывает
сравнение бюджета и платного. В восстановительной схеме такое поле убирается,
а `additionalProperties=false` запрещает его подставлять. Условия сравнения
сохраняются отдельно в метаданных истории (`_comparisons`), даже если SQL
вернул записи только за один год или одну форму. Явное уточнение одного
года/формы заменяет сравнение обычным фильтром. Дополнительного LLM-судьи нет.

Полная выборка без ограничения года/формы покрывает запрошенный поднабор.
Противоречащий год, форма, уровень или код не покрывают его. Поиск новых
названий и алиасов по-прежнему выполняет инструмент: guardrail не является
полным парсером русского языка и не доказывает правильность каждой фразы
модели после успешного запроса.

## Регрессия

Обезличенный сценарий: «Какой проходной балл на 09.03.01?» → ответ только
с проходным → «а средний бал какой?». Провайдер сначала выдаёт ошибочное
«Среднего балла в базе нет» без инструмента. Ожидается восстановительный
запрос `metric=average`, правильное число и отсутствие черновика в транспорте.
Продолжение: другой год → платное обучение. Отдельно проверяются неверные
фильтры, пустая выборка, ошибка и исключение, отсутствие контекста,
ограничение восстановления и перенос параметров через историю Redis.

`tests/pipeline/test_score_guard.py` проверяет границу генерации и публикации;
`tests/pipeline/test_tools_admission_scores.py` — восстановление с настоящей
PostgreSQL и сохранение фактических параметров. Контракт обязательного вызова
проверяется в `tests/llm/test_required_tools.py` и `tests/llm/test_deepseek.py`.

До реализации проблема воспроизведена на сохранённом входе настоящего диалога:
один полный прогон и пять повторов этапа генерации дали ложное отсутствие 6/6.
Экспериментальный guardrail на том же входе дал правильный ответ 6/6
(пять восстановлений). Это проверка прототипа, а не замер этой ветки на проде.
Рабочая история и ключи в репозиторий не включены. Задача: #424.
