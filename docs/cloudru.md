# Эмбеддинги Cloud.ru

Провайдер `cloudru` подключён только для эмбеддингов. Генерация ответов и графа
остаётся у выбранного текстового провайдера (например, DeepSeek).

В админке доступны API-ключ `CLOUDRU_API_KEY` и модель
`CLOUDRU_EMBEDDING_MODEL=ai-sage/Giga-Embeddings-instruct-3B`. Ключ сохраняется
зашифрованным и не возвращается клиенту. Адрес API фиксирован:
`https://foundation-models.api.cloud.ru/v1/embeddings`.

FAQ и LightRAG используют эту же модель. Подтверждённая отдельным запросом
17 ноября 2026 размерность — 2048. Старый `EmbeddingsGigaR` использовал 2560:
совместное использование старых векторов и новой модели недопустимо. Смена
селектора на наполненной базе блокируется до offline-пересчёта.

## Перенос наполненной базы

1. Сделать резервную копию SQL и каталога LightRAG. Остановить **все** API,
   bot и scheduler именно переносимого стенда. Не запускать параллельно импорт
   документов, обработчики очереди и другую миграцию эмбеддингов.
2. Запустить `uv run python -m tools.reembed_cloudru --offline`, передав JSON
   через stdin: ключ `CLOUDRU_API_KEY`, при необходимости модель
   `CLOUDRU_EMBEDDING_MODEL`. Секрет нельзя передавать в argv, коммитить или
   сохранять в открытые отчёты. При использовании контейнера команду выполнять
   в одноразовом worker с теми же конфигурацией и хранилищами стенда.
3. Процедура сначала проверяет подключение, затем пересчитывает chunks,
   entities, relationships и FAQ/aliases в отдельной копии. Исходные тексты,
   идентификаторы и граф сохраняются. На успешном завершении переключаются
   оба embedding-селектора; текстовая модель не меняется.
4. Проверить результат и запустить стенд. Проверить точный FAQ и вопрос по
   документу. Порог FAQ отдельно требует проверки на перефразировках новой
   модели; процедура сама его не понижает и не меняет промпты.

В `embedding-migration-*` сохраняются старый индекс, старый FAQ-кэш и закрытый
`settings-before.json` с зашифрованным снимком настроек. При ошибке оставить
стенд остановленным и проверить этот каталог. Если присутствует
`needs-recovery.json`, проверить фактически сохранённую ревизию SQL перед
возвратом файлов и настроек. Не запускать стенд с индексом одной модели и
настройками другой. Архивы не удалять до проверки поиска.

Пересчёт использует канонические тексты существующего файлового JSON-индекса;
для PostgreSQL storage эта команда отказывает. Индексация заново через LLM не
выполняется. Сетевых повторов внутри адаптера нет: при ошибке или неверных
векторах перенос прерывается, ошибка не содержит ключей или текста документов.

## Изоляция измерений #470

Старое разрешение на 10000 токенов из пакета GigaChat не является разрешением
на расходы Cloud.ru. После переноса нужно отдельно зафиксировать новый
провайдер, модель, 2048 координат, версию пересчитанной БЗ, рублёвый тариф и
границы расходов. Учёт OAuth/GigaChat нельзя использовать как учёт Cloud.ru.
Не открывать provider egress и не начинать пилот автоматически после деплоя кода.
