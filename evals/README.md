# Оценка продуктового пайплайна

Оба режима вызывают `pipeline.llm_client.ask_local_llm`, а не `query_graph`.
Набор берётся только из YAML. Генерации, сна и случайных сценариев в прогоне нет.
Сценарии выполняются с семафором (`--concurrency`, по умолчанию 3), таймаутом
180 секунд и отдельным `session_id=eval:<run UUID>:<case id>` для каждого вопроса.

## CI без ключей и хранилищ

```powershell
$env:PYTHON_DOTENV_DISABLED = '1'
uv run python -m evals.evaluator --offline --report eval-report.json
```

В Linux: `PYTHON_DOTENV_DISABLED=1 uv run python -m evals.evaluator --offline`.
Offline требует отключить dotenv **до импорта** приложения. Использует
in-memory историю, временный FAQ-индекс, детерминированные эмбеддинги,
фиктивные retrieval/provider/tool-зависимости. Реальные FAQ matching,
раскрытие аббревиатур, порядок пайплайна и передача tool executor сохраняются.
Значение 246 в фикстуре — тестовые данные, не проходной балл НГУ.

Этот режим проверяет сборку пайплайна, не качество живой модели, CRAG-грейдера
или SQL-запросов. Регрессии abbreviation/FAQ/tool-loop должны ломать гейт;
это отдельно проверено тестами. Не запускайте offline fixtures внутри работающего
API/бота: они временно подменяют зависимости процесса. CI запускает отдельный процесс.

`requires_llm=false` отмечает случаи, пригодные для изолированного CI-режима.
Это не обещание, что живой пайплайн с тем же вопросом не вызовет модель/эмбеддинги.

## Живой прогон

```bash
uv run python -m evals.evaluator --report eval-report.json
```

Он расходует вызовы модели/эмбеддингов и использует настроенные PostgreSQL,
Redis и RAG. Сначала явно загружает FAQ и аббревиатуры из БД, не создаёт базу,
не запускает миграции/сиды. Ошибка загрузки не маскируется пустым FAQ.
Префикс eval изолирует историю диалогов, **не хранилища**: пайплайн может писать
аналитические логи и Redis-историю. Используйте отдельное тестовое окружение.
CLI не включает живой режим в CI. API `/evals/run` сохраняет живое поведение;
поля `total`, `passed_perfectly`, `rag_results`, `faq_results` сохранены, добавлены
`results`, `mode`, `pass_rate`, `skipped_ids`. Ни один live-прогон не выдаётся
за проверку развёрнутого продукта только по успешному offline CI.

## Формат сценария v1 (необходимая основа #245)

Документ содержит `schema_version: 1` и непустой список `scenarios`.
Каждый сценарий: уникальный стабильный `id`, `question` (вход пользователя),
`reference_answer`, `topic`, `source`, `approved_by`, `approved_at`,
`requires_llm`, `assertions`, необязательные `judge_criteria` и `min_score` (1–5,
по умолчанию 4). Неизвестные поля, дубликаты ID и неверные ассерты отвергаются.
Reviewer/date задаются вместе. `null/null` означает **не подтверждено экспертом**;
миграция старого набора не является экспертным подтверждением ответов.

Ассерты (все должны выполниться):

| kind | value | Смысл |
| --- | --- | --- |
| contains / not_contains | непустая строка | Подстрока без учёта регистра |
| regex | валидное регулярное выражение | Поиск без учёта регистра |
| tool_called | имя инструмента | Реальный trace исполнения, не упоминание в ответе |
| faq_match | bool | Фактическая ветка FAQ |
| refusal | bool | Лексический признак отказа; сам по себе не доказывает безопасность |

Судья вызывается только при `judge_criteria` и успешных детерминированных
ассертах. Рубрика v1 закреплена в `judge.py`, температура 0, порог 4/5.
Температура 0 уменьшает вариативность, но не гарантирует идентичные оценки.
Вложенный JSON разбирается целиком; невалидная оценка/таймаут/ошибка провайдера
дают провал сценария, а не успешный ответ-заглушку. В отчёт ошибок попадает
только тип исключения, не потенциальные секреты из текста ошибки.

## Baseline и коды выхода

`baseline.json`: `schema_version: 1`, `cases: {id: {passed: true}}`;
для live baseline можно добавить `min_score`. Отсутствующий baseline-case —
регрессия, а не пропуск. Baseline обновляется только отдельной правкой на ревью,
прогон никогда его не перезаписывает. `--baseline` позволяет сравнить с сохранённым
предыдущим baseline того же набора. `--min-pass-rate` по умолчанию 1.0.
Для live-набора пока нет измеренного исторического baseline оценок судьи.

- 0: baseline соблюдён, порог достигнут.
- 1: деградация baseline или доля успешных ниже порога.
- 2: ошибка конфигурации/файла.

CI-job `evals-offline` возвращает ненулевой статус при провале и сохраняет JSON
как artifact. Это не изменение защиты `main`: required checks в ruleset
этой задачей не добавляются. При merge агент обязан дождаться успешных проверок.

## Генерация черновиков вне прогона

```bash
uv run python -m evals.generate --input reviewed-excerpts.yaml --output drafts.yaml
```

Вход — явный список `{source: ..., content: ...}` выбранных текстов. Команда
вызывает модель, добавляет сценарии с `approved_by/at=null` в YAML и не читает
боевые chunk-файлы автоматически. Дубликаты ID отвергаются. Выход нужно проверить
человеку, добавить ассерты/подтверждение и включить в статический набор отдельным PR.
