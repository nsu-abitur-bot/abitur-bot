## Критерии ответов

У `document` есть обязательные факты, применимая кампания, источники и их разделы.
Режим `all` требует все факты, `at_least` - указанное минимальное число.
Краткая эквивалентная формулировка допустима. Общий отказ или перенаправление
не заменяют доступный фактический ответ. Сведения одного года, программы или
категории поступающих не переносятся на другие.

Пять `special` проверяют полезные уточнения, осторожность прогноза и помощь
в выборе без решения за человека. Простой отказ без полезного следующего шага
недостаточен. Их доля считается отдельно от ответов по документам.

У вопроса могут быть `history`, допустимые названия и интервалы. Бот получает
только вопрос и заданную историю. Эталон и рубрика передаются судье отдельно.
Дополнительные детали проверяются по источникам. Отсутствие детали в кратком
эталоне само по себе не доказывает, что она выдумана.

## Проверки без моделей

Из backend с отключённым dotenv:

```powershell
$env:PYTHON_DOTENV_DISABLED = '1'
$env:UV_NO_ENV_FILE = '1'
uv run --no-sync python -m evals.validate_admission
uv run --no-sync python -m evals.validate_admission --require-reviewed
```

Обычный валидатор проверяет формат, уникальность, квоты, группы, источники,
SHA YAML и целостность записей ревью. Строгий требует 50 внутренних подтверждений.
При текущих 50/50 он проходит. Это проверка целостности подтверждений, не качества
бота. Основание записано со слов Михаила, экспертных подтверждений 0/50.
Технические offline-сценарии в `evals/scenarios.yaml` ведутся отдельно.

## Живой прогон

В изолированном `with-kb` сохранены девять источников. SQL, граф и векторы
проверены после загрузки. [История индексации](../../docs/reports/388-indexing-eight-2026-11-07.md)
сохраняет все попытки и измерения. Повторная индексация этой редакции для прогона
не нужна. `empty-kb` использует отдельные PostgreSQL, Redis и файловый том.
Общие базы и действующие диалоги не очищаются.

`tools/admission_full_control.py` выполняет по пять партий из десяти вопросов
для каждого условия. `tools/admission_full_batch.py` использует настоящий
PipelineEvaluator с отдельными сессиями, четырьмя калибровками судьи и новым
процессом для каждой партии. Промпты и эталоны во время сравнения не меняются.
Общий расчётный предел DeepSeek - 5 CNY. Usage, intent, версии, ошибки,
время и память сохраняются. Технический отказ останавливает следующие партии,
автоматического повтора вопросов нет. Установка и запуск описаны в
[инструкции изолированного CLI](../../deploy/evals/388/README.md).

В пустом условии отсутствуют документы, FAQ, чанки, наполненные графы,
векторные индексы и кэши готовых ответов. После пилота обнаружен служебный
кэш выделения ключевых слов из вопросов. Его происхождение проверено, записи
содержат только тип `keywords` и два списка строк. Такой кэш разрешён отдельно,
кэши ответов и извлечения фактов отклоняются. Это измерение качества с учётом
прогретого кэша запросов, не тест полностью холодного старта.

Все ошибки, таймауты и пропуски остаются в знаменателе 45 или 5. Порог улучшения
с базой по группе document принят Михаилом 11.11.2026 как минимум +20
процентных пунктов. Он принят после запуска 10.11 и применяется к последующим
сравнениям. Исходные условия и оценки завершённого прогона не меняются.
Сравнить сохранённые отчёты без вызовов моделей:

```powershell
uv run --no-sync python -m evals.compare_admission docs/reports/release-388-full-data/with-kb-aggregate.json docs/reports/release-388-full-data/empty-kb-aggregate.json
```

Команда проверяет версии и считает доли по группам. Она не проверяет факты
вместо человека и не выдаёт автоматическую приёмку. Критические нарушения и
спорные оценки разбираются отдельно. При недостижении целей #388 требует
зафиксировать список дефектов. Готовность релиза оценивается по SRS.
