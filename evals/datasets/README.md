# Вопросы о поступлении в НГУ

Refs #388.

В `nsu_admission_2026.yaml` подготовлены 50 вопросов с черновиками ответов.
Они сформулированы по рекомендациям консультационной группы и официальным
страницам. Это не выгрузка пользовательских диалогов. Частота тем по реальным
обращениям не измерялась. Персональных данных абитуриентов в наборе нет.

Распределение соответствует плану #346: до окончания подачи заявлений и
согласий - 32, после зачисления - 10, платное обучение - 8. Внутри этих групп
сохранены все 15 тематических квот. Сравнения включают ММФ, ФФ, ИИР и НГТУ.
Существующие `../scenarios.yaml` и `../university_scenarios.yaml` остаются
техническими проверками и в эти 50 не входят.

## Состав файлов

- `nsu_admission_2026.yaml` - вопросы, ответы, ссылки, ассерты и критерии судьи
  в существующем формате v1. Все вопросы используют `requires_llm: true`.
- `nsu_admission_2026_registry.json` - контекст кампании, разделы источников,
  связь с требованиями, действие, критические ошибки, пробелы и записи проверок.
- [Отчёт #388](../../docs/reports/388-golden-dataset.md) - состояние работы,
  ограничения и порядок приёмки.

Идентификаторы стабильны. Название файла указывает на использованные материалы
кампании 2026, а не на подтверждённый набор для 2027 года. Вопросы о 2027 проверяют
уточнение будущих условий и запрет переноса прошлогодних дат. Контекст,
необходимый боту, включён в сам вопрос. Реестр дополняет его для проверяющего.

## Проверка ответов

Михаил Дешин собирает вопросы и готовит ответы. Марат Тимофеев проверяет
источники и подтверждает ответы внутри команды. Экспертная проверка приёмной
комиссии проводится отдельно. Ревью PR должно охватывать конкретную версию
набора. Общий комментарий «посмотрел» не подтверждает все 50 ответов.

На 03.11.2026 внутренне подтверждено **0 из 50**, экспертно - **0 из 50**.
У 19 черновиков указаны недостающие материалы или разъяснения.
Состояние `draft` у остальных 31 означает только отсутствие уже записанного
пробела, а не готовность или подтверждение ответа.

Для каждого ID проверяющий должен:

1. Проверить вопрос, применимость источника к году и категории поступающего,
   эталонный ответ, критерии и допустимые варианты формулировки.
2. Уточнить спорные факты. Если правильное действие - объяснить отсутствие
   сведений и перенаправить, проверить именно это действие. Недоступная страница
   не доказывает факт из неё. Отсутствие подробностей в обзоре также не
   доказывает отсутствие соответствующего курса, льготы или процедуры.
3. Исправить материалы до подтверждения. Прочитать актуальную версию заново.
4. В `internal_review` указать `status: confirmed`, фактические `reviewer`,
   `reviewed_at` (YYYY-MM-DD), `basis` (источники, разделы и ссылка на отзыв),
   `dataset_sha256`. Установить `content_status: reviewed`, очистить решённый
   `missing_evidence`. Решение о допустимом ответе при недостатке данных нужно
   объяснить в `basis`, а не просто удалить пробел.

Поля `approved_by` / `approved_at` в YAML по правилам текущего каркаса означают
экспертное подтверждение. Для внутренней проверки они остаются `null`.
Когда эксперт действительно проверит ответ, запись добавляется в `expert_review`
с тем же набором полей, а reviewer/date дублируются в YAML.

Корневой `dataset_sha256` - SHA-256 точных байтов YAML. После любой правки YAML
он пересчитывается, прежние подтверждения сбрасываются или заново получаются
для новой версии. Хеши подтверждений нельзя механически заменять без проверки.
При изменении оснований в реестре проверка также повторяется. Проверяющий и дата
не заполняются автоматически по assignee, автору коммита или результату теста.

## Проверки без моделей и хранилищ

Из корня backend в PowerShell:

```powershell
$env:PYTHON_DOTENV_DISABLED = '1'
$env:UV_NO_ENV_FILE = '1'
uv run --no-sync python -m evals.validate_admission
uv run --no-sync python -m evals.validate_admission --require-reviewed
```

Первая команда проверяет формат, уникальность, квоты, полноту реестра, ссылки
между файлами и записи подтверждений. Она может успешно проверить черновик.
Вторая дополнительно требует все 50 внутренних подтверждений и сейчас
возвращает код 1. Повреждённые данные дают код 2. Эти команды не импортируют
приложение, не читают `.env`, не вызывают модели и не подключаются к БД.

Offline-прогон этого набора не оценивает качество ответов: все 50 вопросов
требуют живой модели, поэтому offline их исключает. Для проверки технического
каркаса остаётся прежний набор `../scenarios.yaml`.

## Проверка качества на стенде

Запускать после внутреннего подтверждения, подготовки отдельного окружения
и согласования расхода внешних моделей. Рабочую БД и production-ботов для этого
не использовать. Окружение настраивает ответственный за стенд через штатный
механизм, без копирования секретов в репозиторий. До загрузки приложения
отключить dotenv. Идентификатор `eval:` разделяет историю, но не изолирует БД.

Сначала зафиксировать commit кода, SHA-256 набора, ревизию настроек, имена
моделей ответа, графа, эмбеддингов и судьи, версии FAQ/сокращений и материалов
базы знаний. Для недоступных источников загрузить проверенные документы либо
согласовать ожидаемое уточнение. Из эталонных ответов нельзя молча создавать
FAQ и затем представлять совпадение с ним как качество поиска по документам.
Если отдельно измеряется FAQ, этот режим и способ наполнения указываются явно.

Для выполнения используется `PipelineEvaluator` из `evals.evaluator`:

```python
import asyncio
import json
from pathlib import Path

from evals.validate_admission import validate_dataset

summary = validate_dataset()
if summary['internal_confirmed'] != 50:
    raise SystemExit('Набор ещё не подтверждён')

from evals.evaluator import PipelineEvaluator

report = asyncio.run(PipelineEvaluator(
    'evals/datasets/nsu_admission_2026.yaml', concurrency=1
).run())
report['dataset_sha256'] = summary['dataset_sha256']
report['target_pass_rate'] = 0.90
Path('admission-live-report.json').write_text(
    json.dumps(report, ensure_ascii=False, indent=2) + '\n', encoding='utf-8'
)
```

Это пример для подготовленного тестового процесса, не команда для текущей
рабочей сессии. Он вызывает модели и может писать историю и аналитику в
хранилища стенда. Настройки запуска и версии данных прикладываются к результату.
Старый `evals/baseline.json` к этим ID не применяется. Измеренного baseline
для нового набора пока нет.

После прогона проверить наличие результатов всех 50 ID. Доля успеха считается
среди всех 50: ошибки, таймауты и пропуски дают неуспех. Для цели 90% нужно
не менее 45 успешных ответов. Марат отдельно проверяет ответы на критические
нарушения из реестра и записывает затронутые ID, нарушение и основание.
Оценка LLM-судьи не заменяет эту проверку. При критическом нарушении готовность
не подтверждается независимо от общей доли успеха.

При ошибках подготовить список дефектов с примерами и ссылками на результат,
не подгонять эталоны под ответ модели. Сохранённый отчёт затем используется
в #390 с той же областью измерения. Повторный замер нужен при изменениях
данных, кода, конфигурации или обнаруженной ошибке методики.
