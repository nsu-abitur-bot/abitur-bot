# Проверка #388 без сервера API

CLI установлен администратором. 10.11.2026 выполнены пилот 10+10 и полный
прогон 50+50 партиями, без API. [Результаты и ограничения](../../../docs/reports/388-full-evaluation-2026-11-10.md).
Испытательная конфигурация имеет профиль custom и пустой справочник программ,
её результаты не заменяют приёмку рабочего демостенда НГУ.

## Устройство режима

Новая команда имеет вид:

```sh
sudo -n /usr/local/sbin/abitur-eval388 with-kb cli-run \
  /evaluation/admission_memory_probe.py --execute
```

`cli-run` использует тот же закреплённый образ и существующую конфигурацию
тестового варианта. Поднимает только PostgreSQL и Redis без зависимостей,
затем запускает одноразовый контейнер с Python вместо uvicorn.
API-сервер, бот, scheduler и миграции не запускаются. Допускаются только
Python-файлы непосредственно из `/evaluation`, параметры передаются после
имени сервиса и не превращаются в параметры Docker.

Сохраняются порог 1100 МиБ доступной RAM, минимум 5 ГиБ диска, запрет
параллельных вариантов и лимиты API-профиля 640 МиБ RAM / 896 МиБ RAM+swap /
0,75 CPU. PostgreSQL ограничен 128 МиБ, Redis 32 МиБ. Если фактическая
root-конфигурация не соответствует проверяемым условиям, новый режим отказывается
запускаться. Эти условия не меняют legacy-команды wrapper.

CLI-контейнер не публикует порты, работает как 1000:1000, без capabilities,
с read-only корневой файловой системой, отдельным `/tmp` и no-new-privileges.
Существующие тома тестового варианта сохраняют свои назначения. Автоматический
перезапуск и HTTP-healthcheck отключены. Параметры Compose описаны в
[документации Docker](https://docs.docker.com/reference/cli/docker/compose/run/).

На один worker отводится 300 секунд. Wrapper держит общий lock до завершения,
обрабатывает HUP/INT/TERM, после чего удаляет только worker со своим маркером
и останавливает созданный тестовый проект без удаления томов. Ошибка cleanup
попадает в итоговый статус. SIGKILL или отключение сервера требуют ручного
осмотра перед повторным запуском. Чужой контейнер с совпавшим именем не удаляется.

## Что измеряет программа

`tools/admission_memory_probe.py` сначала загружает настройки экземпляра из
тестовой БД. Затем импортирует GraphMemory, копирует фиксированный перечень
файлов девяти документов в `/app/data/.memory-probe-<run_id>/abitur_kb` и открывает
LightRAG на этой копии. Хеши копии сверяются до загрузки, исходные файлы - после.
Копия остаётся для осмотра, оригинальный индекс не используется для записи.

Фиксируются этапы импорта, копирования, загрузки хранилищ и закрытия:
пиковая память cgroup, максимальный RSS процесса, swap, OOM-счётчики и минимум
доступной RAM хоста. Наблюдение идёт каждые 0,2 секунды. При падении доступной
RAM ниже 300 МиБ программа записывает отказ и завершается. Это дополнительная
остановка, начальный порог 1100 МиБ не снижается.

Сетевой audit hook разрешает только подключения к собственным PostgreSQL и
Redis. Попытка обращения к провайдерам или внешней загрузки словаря отклоняется.
Отсутствующий словарь нужно подготовить в образе, не скачивать во время замера.
Вопросы, поиск по вопросу, генерация и эмбеддинги не запускаются.
Результат: `/reports/cli-memory-<run_id>.json`. В нём только метрики и разрешённые
метаданные. stdout/stderr worker не передаются в вывод root-wrapper.

Успешная загрузка хранилищ не доказывает готовность ответа на вопрос: затраты
поиска, промежуточных данных и генерации остаются отдельным измерением.
Копирование файлов также входит в ресурсный профиль этого пробного запуска.

## Проверки подготовки

## Полный набор партиями

`tools/admission_full_control.py` выполняет 50 одинаковых вопросов в двух
условиях. Он вызывает прежний root-owned CLI по десять вопросов, каждый раз
в новом worker. Ресурсы и настройки общих сервисов не меняются. В конце каждой
партии проверяются результаты, intent, usage и cleanup. При техническом отказе
контроллер останавливается и не повторяет уже отправленные вопросы.

После ревью 11.11 добавлена явная проверка `result.error` в worker и
контроллере. Ошибка разбора судьи или таймаут останавливают следующие вопросы,
даже если все HTTP-запросы завершились и usage полный. Неуспешный результат
сохраняется до остановки. Обычный `passed=false` без технической ошибки
продолжать разрешено. Исправление подготовлено в PR, серверная копия запуска
10.11 сохранена. Перед будущим запуском нужен новый проверенный пакет с SHA,
не подмена кода или отчётов завершённого запуска.

`tools/admission_full_batch.py` проверяет разрешение полного прогона, точный
SHA набора, состав 45/5, закреплённый образ и код. Новый процесс получает
только свою фиксированную десятку. Судья проходит четыре контрольных примера.
Ошибки ответов сохраняются как неуспехи, промпты и эталоны не меняются.

Общий расчётный предел DeepSeek - 5 CNY для обоих условий. Предыдущие расходы
считаются по сохранённым usage по пиковой ставке без кэша. Перед каждой партией
журналы копируются в отдельные evidence-файлы, SHA и остаток проверяет worker.
Неполный usage, дубликаты, пропуски и ошибка cleanup блокируют следующую партию.
Порог RAM хоста 1100 MiB и лимит worker 640 MiB сохранены. Лимит 512 HTTP на
партию отделён от общего бюджета. Изначальный исполнитель пилота остаётся
ограниченным десятью вопросами и не принимает план полного набора.

### Результаты пилота

Счётчик учитывает HTTP-сжатие отдельно от SDK. Для разбора SSE используется
собственный декодер HTTPX, исходные байты передаются приложению без изменений.
Регрессионные проверки покрывают identity, gzip, deflate и zstd, включая
поток с отсутствующим usage или терминатором. При продолжении учитываются
сохранённые расходы прошлых попыток и точные сессии старых служебных логов.
История новых вопросов по-прежнему должна быть пустой. Сброса хранилищ нет.

Статус на 10.11: ошибка чтения сжатого zstd-потока исправлена, пилот 10+10
завершён. Судья засчитал 5/10 с базой и 0/10 без базы, один зачёт спорный.
Пик с базой 640 MiB, swap 51,3 MiB, OOM 0. Полный прогон не запускался.
[Ответы, расходы и ограничения](../../../docs/reports/388-pilot-completion-2026-11-10.md).

`tools/admission_pilot.py` исполняет только фиксированные 10 сценариев в каждом
условии. Режима 50 вопросов в нём нет. Версия набора и исходников образа сверяется
до запросов. `--inspect-only` проверяет конфигурацию и пустоту/наполнение без
обращений к провайдерам. Конфигурации двух условий сравниваются до платного пилота.

Каждый вопрос выполняется последовательно через существующий PipelineEvaluator,
с новой сессией и лимитом 90 секунд на ответ вместе с оценкой. Сначала судья
проходит четыре контрольных примера. Детерминированные ассерты сохраняются.
Ошибки и таймауты остаются неуспехами. После каждого случая сохраняются ответ,
оценка, время и память. Повтор вопросов автоматически не выполняется.

На условие установлен расчётный предохранитель 5 CNY по пиковым ставкам без
кэша и максимум 256 HTTP-попыток. Это не финансовый лимит провайдера.
Перед отправкой сохраняется intent без текста/заголовков и выполняется fsync,
после ответа сохраняется usage. Незавершённый запрос виден по расхождению
журналов и блокирует следующие обращения. Итоговый расход включает судью,
эмбеддинги, калибровку и неуспешные попытки отдельно от индексации.

Локальные unit-тесты выполняют команды через синтетический исполнитель, без
Docker, серверной БД и моделей. Они проверяют отказ по ресурсам и чужим
контейнерам, запуск без зависимостей, timeout, прерывание, cleanup и ограничения
корневой конфигурации. Это не доказательство развёртывания режима на сервере.
